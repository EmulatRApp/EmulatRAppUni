Boot Acceleration - Entry Snapshot

EmulatR can skip re-running the guest self-decompression on a subsequent run by capturing a complete-machine snapshot at the firmware's own init-to-console handoff and restoring it. The handoff is the point where the decompressor stub transfers control into the decompressed console -- the entry PC the image declares, entryPa = targetPalBase + finalPC, the same point the decompressor internals describe. The feature is governed by the EMULATR_FAST_DECOMPRESS environment lever and is OFF by default: with it unset EmulatR always runs the faithful decompressor and is the Oracle.

 

The lever

Set EMULATR_FAST_DECOMPRESS before launching:

 

•unset or faithful -- the Oracle default: run the guest decompressor on every init.

•snapshot (or 1) -- on the first run, decompress faithfully and MINT a snapshot at entryPa; on a later run, REUSE that snapshot to skip the decompressor.

 

The convenience wrapper tools/es40_fast_decompress.sh {snapshot|faithful} sets the lever and runs the ES40 harness; the same lever works for any SRM firmware (see Model coverage below).

 

How it works

The mint fires once, from the same translated-physical-address handoff detection the console-relocation trigger uses (so it is immune to the PAL-mode bit that a raw PC compare would miss). At that instant the machine is quiescent -- the previous instruction has retired and its writeback is resolved into the CPU state -- so the snapshot is a complete, consistent image: the full CPU state (all registers and IPRs, PC, PAL_BASE, mode), the page-sparse guest memory at its true addresses, and the chipset state. The image the guest decompressor itself produced is captured as-is; EmulatR does not recompute the decompressed layout.

 

On a subsequent run the snapshot is validated and restored, and the boot re-enters at entryPa without re-running the decompression.

 

The snapshot file

The snapshot is written next to the firmware, named for it: firmware/<stem>.axpsnap (for example firmware/es40_v7_3.axpsnap). The name binds the machine state to the exact firmware image it was decoded from. It is a per-run performance artifact: it survives a normal exit, a clean shutdown, and an abort so it remains diagnostically available, and it is regenerated (overwritten) only when a run reaches entryPa and finds no VALID snapshot already in place.

 

Determinism and validation

A restored snapshot must match the run that consumes it, or determinism is lost. EmulatR enforces this with the existing snapshot validator before any restore: a stored checksum plus the CPU-state and chipset format versions plus the chipset VARIANT. Any mismatch -- a rebuild bumped a version, the file is truncated or corrupt, or it belongs to a different platform -- fails the load cleanly and the run falls back to the faithful decompressor and re-mints. A stale-code snapshot can therefore never be silently consumed. Determinism is broken only by a change the validator catches (a code rebuild) or by an input change; it is NOT necessary to delete the file between runs.

 

Restore-except-flash

The snapshot carries the TIG flash / NVRAM image, but a reuse re-points the flash to the CURRENT backing after restore. This means live environment changes -- a set at the >>> prompt, or an update srm, persisted to <stem>.rom / ds10_flash.rom -- are honored on the next run, not reverted to the snapshot's capture-time environment. Real flash is nonvolatile; the restore treats it that way.

 

Model coverage

The lever lives in the shared SRM load path, so it applies uniformly to DS10, DS20, and ES40. Two independent layers keep models isolated: each firmware keys its own <stem>.axpsnap, and the chipset-variant check in the validator blocks an ES40 (Typhoon) snapshot from ever restoring into a DS10 / DS20 (Tsunami) machine. Cross-model, wrong-build, or corrupt snapshots all resolve to a faithful decompress, never to silent corruption.

 

What it does and does not accelerate

The entry snapshot skips the self-decompression -- the roughly four-million-cycle spin at PC 0x60111c -- and the boot up to entryPa. It does NOT by itself skip the post-entryPa silicon-mode initialization (the long real-hardware timing grind); that is addressed by the separate warp knobs. The two are complementary levers.
