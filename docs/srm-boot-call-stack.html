SRM Boot Call-Stack

Before the file list, one scope correction that matters for where you look: `apisrm/ref` is the *platform/chip reference leaf* — drivers (`dq_driver.c`), PAL macros (`ev6_huf_decom.m64`), the defs files (`ev6_defs.mar`, `osfalpha_defs.mar`), the IPR examine/deposit driver (`ev6_ipr_driver.c`). The boot-to-prompt *spine* — the kernel executive, the secondary-start logic, and the shell that actually prints `>>>` — lives in the shared apisrm source dirs, not under `ref/`. So a call stack confined to `ref/` is incomplete by construction; treat ROSETTA_STONE.md's "console shell" and "kernel" sections as the real index. Below I name files where the project has confirmed them and mark the rest `[LOCATE]` with the grep string that resolves them against your live tree.

 

The ordered pipeline, anchored to the ES45/Titan power-up display (which is ground truth in the project knowledge:

 

1.**SROM + image expansion (pre-C).** Serial ROM inits EV6/Bcache, then expands the Huffman-packed console image into RAM and jumps to it (your beep-code-1 "Jump to Console"). Decompressor macros: `ref/ev6_huf_decom.m64` (confirmed). This is the same relocating-copy you already traced at 0x6003ec.

2.**PALcode RESET + console cold entry.** RESET PAL entry establishes PALmode/stack and transfers to the C console kernel. The `starting console on CPU 0` line marks the handoff. PAL: `srmconsole/EV6_OSF_PAL.MAR` + Tsunami layer `EV6_OSF_PC264_PAL.MAR` (confirmed). C entry: `[LOCATE: grep "starting console on CPU"]`.

3.**Kernel executive init.** semaphores, heap, driver structures, idle PCB/PID, file system, timer structures, lower IPL, then `create dead_eater / poll / timer / powerup`. This is the multithreaded console RTOS. `[LOCATE: grep "initializing semaphores" / "initializing heap"]` — this file is the scheduler core.

4.**Platform + chipset bring-up.** access NVRAM, memory test/config, probe I/O subsystem, PCI hose probe, driver attach (`pka`, `eia`, `dqa`...). Tsunami init. `[LOCATE: grep "probe I/O subsystem" / "probing hose"]` for the platform module; drivers attach from `ref/` (`dq_driver.c` confirmed, plus `pk*`/`e*`). None of these are required to *reach* the prompt — a failed `dqa` logs and continues.

5.**MP secondary bring-up — this is the stage DS10 never executes.** `starting console on CPU 1`, `CPU 1 speed is...`, etc. The primary builds each per-CPU HWRPB slot, signals the secondary via an implementation-specific hardware register, and the secondary polls its RXRDY flag and runs its idle PCB. `[LOCATE: grep "starting console on CPU" / "secondary"]`.

6.**Banner + prompt (the shell).** `SRM Console Vx.x...` then the prompt. `>>>` is the uniprocessor form; `P%02d>>>` is the MP form, the `%02d` filled from the primary's WHAMI. `[LOCATE: grep ">>>" and "P%" — the literal lands you directly on the shell's prompt builder; grep "whami" in that same file for the CPU-number source]`.

 

Now the part you actually care about. The reason DS10 reaches `>>>` and DS20 stalls is almost certainly stage 5, and the project already contains the smoking gun: V4's `execCserve` is hardcoded uniprocessor. `CSERVE$WHAMI` (0x41) returns a literal 0 with the comment "V4 is uniprocessor... revisit when an MP profile lands," and `CSERVE$START` (0x42) is a deliberate no-op ("on a UP model there are no secondaries to start; return with nothing done"). On a DS20 the console *expects* two CPUs, so it enters the stage-5 rendezvous, signals CPU1, and waits for CPU1 to set the per-CPU slot flags (PV/PMV/CV/BIP). With START no-op'd and no second CPU actually running, that wait never completes — so you hang somewhere after the last successful stage-4 message and before the banner.

 

That also answers your doubt about the harness. You're right that the deterministic-async CPU harness won't be enough on its own. The harness gives you two CPUs with coherent LDQ_L/STQ_C and ordered memory — which is the *substrate* the rendezvous needs (primary selection is a shared single-bit mutex via LL/SC per arch-ref 27.8.1.1, and the RXRDY/TXRDY channel is shared memory). But sitting on top of that substrate, you still need three things the harness doesn't provide:

 

- A **Tsunami secondary-wakeup path** — the implementation-specific register the primary writes to release CPU1 (on this chipset family that's a Cchip MISC/IPIR-style CSR). Without it, CPU1 never leaves its console spin even if the harness is scheduling it.

- **Per-CPU WHAMI** returning the real CPU id, not a hardcoded 0 — both for the prompt format and so each console instance indexes the correct per-CPU slot.

- The **per-CPU slot flag handshake** honored end to end (CV → BIP/RC → PV/PMV), which means `CSERVE$START` has to actually do something on the MP model instead of no-op'ing.

 

The fastest diagnostic to confirm all of this before you build any of it: **what is the last console line printed before DS20 goes quiet?** If it stops right after a stage-4 line (drivers/probe) and before any `starting console on CPU 1`, the console is hanging entering the rendezvous — likely reading a 2-CPU count from the chipset and then blocking. If it prints `starting console on CPU 1` and *then* hangs, it's inside the START/poll loop waiting on CPU1's slot flags. Either way the last line localizes the stall to a single file you can then `[LOCATE]`.

 

And a tactical fork worth weighing: if your near-term goal is just to *get DS20 to `P00>>>`*, the cheap path is to make the platform/chipset config report a single present CPU so the console skips stage 5 entirely (you'd still get the MP `P00>>>` prompt from the MP console build, just no secondary wait). Standing up the full two-CPU rendezvous — wakeup CSR, per-CPU WHAMI, START semantics, slot-flag dance on top of your harness — is the real SMP milestone and is separable from reaching the prompt.
