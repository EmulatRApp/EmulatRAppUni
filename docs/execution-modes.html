Execution Modes: Virtual (ISP) vs REAL_HW

The Alpha console firmware runs in one of two modes, and the choice changes its entire initialization strategy. Virtual mode (ISP) is DEC's pre-silicon software simulator path: the firmware assumes it runs on the Instruction-Set-Processor engineering model rather than on chips, and deliberately skips the real-hardware probe, timing, and device-driver-attach steps. REAL_HW is the actual-silicon path: the firmware drives the full probe, reset, timing, and attach sequences. EmulatR answers "virtual (ISP)" by default, which is why the console reaches the operator prompt cleanly and quickly, and equally why real device discovery does not happen in that mode.

 

The mode flag: platform()

The firmware carries its own detector: a single 32-bit read of physical address 0x0000_BFFC. On the ISP simulator, DEC's startup deposits the sentinel 0xCAFEBEEF there; on real hardware that location holds something else, so the detector returns REAL_HW.

 

int platform( ) {

 /* ISP flag at 0xBFFC. ISP startup deposits 0xCAFEBEEF there. */

 if ( (*(int *)0xBFFC == 0xCAFEBEEF) )

 return ISP_MODEL; /* pre-silicon software simulator */

 else

 return REAL_HW; /* actual silicon */

}

 

Reference: apisrm pc264.c:173; ISP_MODEL / REAL_HW defined in pc264_io.h and emulate.h (ISP_MODEL = 1).

 

How EmulatR selects the mode

EmulatR does not deposit anything into memory; it presents the sentinel as a read intercept, so the value survives the SRM self-decompressor (which overwrites image offset 0x3FFC == PA 0xBFFC, so a one-time store would not last). The environment knob EMULATR_PLATFORM selects the mode at runtime; no rebuild is needed.

 

// EMULATR_PLATFORM unset|"isp" => ISP (default; reaches >>>)

// "silicon" => REAL_HW (no intercept)

if (s_isp && pa == 0x000000000000BFFCull)

br.data = 0xCAFEBEEFull; // platform() => ISP_MODEL

 

Reference: pipelineLib/MemDrainer.h:458-486. There is intentionally one flag; the firmware's own platform() is the single source of truth.

Why ISP is fast and silicon grinds

The single mechanism behind the speed difference is the micro-delay. In virtual mode krn$_micro_delay returns immediately; in silicon mode it busy-waits on the scaled cycle counter (RSCC) for the full requested interval. Probe and reset sequences call it constantly, so silicon mode spends millions of emulated instructions spinning where ISP mode spends none.

 

void krn$_micro_delay (INT us) {

if (platform() == ISP_MODEL) return; // ISP: no delay at all

cpm = cycles_per_microsecond;

rscc(&start); // CALL_PAL RSCC

limit = (cpm * us) + start;

do { rscc(&stop); } while (stop < limit); // silicon: busy-wait on RSCC

}

 

EmulatR models RSCC = cycleCount/5594. The faithful acceleration for silicon mode advances cpu.cycleCount coherently during a recognized pure delay spin so RSCC crosses limit and the loop exits (the same approach as EMULATR_IDLEWARP). It must never blindly jump the counter or write timebase state out-of-band; the quarantined EMULATR_RSCCWARP did (rewriting 0x3c970) and corrupted the boot.

 

Choosing a mode

Virtual (ISP) is the frozen faithful-oracle-to-prompt mode: it reaches P00>>> with device presence via the topology walk, but no device datapath. REAL_HW is required for actual device discovery and, eventually, OS boot -- but it runs to completion only once the real-hardware timing loops are modeled or warped past. Any device or behavior the firmware gates behind platform() == REAL_HW is invisible in ISP mode, no matter how faithfully the device itself is modeled -- so mode is the first thing to check when reading a "device not discovered" symptom.
