Execution Matrix (Models x Modes)

A quick reference for the testing teams: each supported model crossed with its two execution modes -- Virtual (ISP) and REAL_HW (Silicon) -- plus the orthogonal firmware.axpsnap snapshot accelerator, and what each combination is expected to reach TODAY. Cells describe current, verified behavior; open diagnostics are cross-referenced to the Known Gaps IDs (G-nn). With every lever unset, all models run the faithful decompressor on the ISP default and constitute the deterministic Oracle.

Mode and lever legend

•Virtual / ISP (Engineering) -- the DEFAULT (EMULATR_PLATFORM unset). The 0xBFFC platform read is intercepted to return 0xCAFEBEEF, krn$_micro_delay returns immediately, and no real device discovery runs. Fastest path to the console.

•REAL_HW / Silicon -- opt in with EMULATR_PLATFORM=silicon. Real RSCC-based micro-delay timing and the device-discovery path are exercised; pair with EMULATR_IDLEWARP to make the timing grind practical.

•firmware.axpsnap -- opt in with EMULATR_FAST_DECOMPRESS=snapshot. Orthogonal to the two modes: it captures a complete-machine snapshot at entryPa and restores it, skipping the guest self-decompression. Per-firmware keyed (firmware/<stem>.axpsnap), restore-except-flash, validated by checksum + version + chipset variant.

 

Other testing considerations

•Determinism / Oracle: all levers unset => faithful decompressor + ISP default = the deterministic Oracle. Warp, snapshot, and silicon are all opt-in and must be named when a run trades determinism.

•Warp knobs: EMULATR_IDLEWARP is safe. EMULATR_RSCCWARP is QUARANTINED (jumped ticks corrupt the boot) -- do not enable it.

•Output placement: run and console logs go to ./logs, execution / retire traces to ./traces, timestamped purpose_YYYYMMDD_HHMMSS.ext.

•Cross-model isolation: a snapshot never restores across chipset families -- a Typhoon (ES40) snapshot cannot load into a Tsunami (DS10 / DS20) machine; a mismatch falls back to a faithful decompress.
