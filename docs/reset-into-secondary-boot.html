Reset into Secondary Boot (CSERVE START Handoff)

This topic documents the execution mode EmulatR enters when the SRM console hands control to a secondary bootstrap -- the guest operating-system loader. It covers the reset re-entry after firmware decompression, the PALcode power-up path (sys__reset / sys__reset_init), and the CSERVE START handoff that restores the OS context and transfers to the loaded image. The walk-through is DS20-specific (ds20_v7_3) but the mechanism generalizes to DS10 and ES40. All addresses and instruction encodings are taken from live EmulatR DIAG-PC, FaultEventLog, and PA-watch traces; values are runtime-observed unless noted.

The durable architectural lesson, established once boot0 actually executed, is stated up front: the OS-boot handoff is a SEQUENCE of CALL_PAL CSERVE functions, and each must RUN THE GUEST PALcode -- not be intercepted and replicated in C++. The rest of this topic derives that lesson from the live evidence.

 

The handoff at a glance

On EV6, transferring from the SRM console to the operating system is a PAL restart, not a plain jump. The console boot command (ref/boot.c) first builds the 3-level page table (VA 0x20000000 -> base_pfn), populates the per-CPU HWRPB slot, and writes the restart context into the impure / CNS save area. It then invokes CSERVE START, and PALcode runs cfw_start -> sys__exit_console -> pal__restore_state -> HW_REI to the OS entry at 0x20000000. restore_state reconstructs the OS context by dereferencing p_temp (register r21) then PT__IMPURE(p_temp) then the CNS save frame -- from which it restores PTBR, PC, PS, SP, the GPRs, and FPCR. A valid p_temp is the precondition for a correct restart, and -- critically -- the restart must carry the OS execution MODE (PS / IPL / VPTB), not just the PC.

 

The faithful handoff sequence (sys__exit_console)

This is the reference mechanism the guest PAL runs, from the DEC apisrm source (read-only authority). Option A drives EmulatR into exactly this code:

cfw_start (ev6_vms_pc264_pal.mar:3956): br r31, sys__exit_console

sys__exit_console (:4245):

bsr p7, pal__restore_state ; restore PTBR/PC/PS/SP/GPRs/FPCR from the CNS save area

hw_mtpr r31, EV6__ITB_IA ; flush ITB (clears any stale 0x20000000)

hw_mtpr r31, EV6__DTB_IA ; flush DTB

... set up + tear down the 1:1 mapping, clear locks ...

hw_mtpr r31, EV6__IC_FLUSH ; flush icache

hw_ret_stall (p23) ; RESTART at the restored PC (0x20000000)

pal__restore_state (ev6_vms_pal.mar:6228): hw_ldq/p r1, PT__IMPURE(p_temp) ; then CNS__PTBR/PC/PS/SP/GPRs/FPCR

The terminating hw_ret_stall(p23) is what makes the PAL linkage register p23 load-bearing: it is the RESTART, and it uses R23. Any handoff that reaches this instruction with a stale R23 restarts to the wrong place (a reset).

 

The defect: CSERVE START stubbed as a no-op

The firmware-to-OS handoff at VA 0x20000000 is CSERVE function 0x42 (START). EmulatR's dispatch (palBoxLib/grains/PalEntries.cpp, case 0x42, ~line 628) originally stubbed it: "no secondaries to start; return with nothing done." That is correct for an SMP-secondary start, but WRONG for the PRIMARY boot transfer, which routes through the same START -> sys__exit_console path. The no-op strands the whole handoff -- no PTBR install, no ITB flush, no restart -- and HALTs at 0x20000000. It is also why AXPBox / es40 boot VMS and a stubbed V5 did not.

Live reproduction (DS20, Mac; DIAG probes compiled in): with EMULATR_PTBR_DIAG=1 and EMULATR_ITBPROBE_VA=0x20000000, driving b dqa0 shows CSERVE entry func=0x42 START pc=0x1ae398 cyc=874809139, then halted CPU 0 / halt code = 0 / PC = 20000000. The diagnostics confirm it is the RESTART, not translation: PTBR writes (SWPCTX) = 0 and ITBPROBE 0x20000000 hits = 0. VMB ran (cyc ~184M -> 874M setup), then START fired immediately before the halt.

 

The reset re-entry path

To reach a correct START, sys__reset must complete. After the decompressor inflates the console/PAL image, its final hw_ret is routed to the PAL power-up vector, NOT the console entry. The power-up vector branches to sys__reset, which flushes the translation buffers and programs the Ibox/Mbox control registers before reaching the scaffold instruction.

The unassigned-IPR (0x2d) scaffold

At 0x13654, sys__reset executes HW_MTPR r?,<scbd 0x2d> (encoded 0x77e72d40) -- a write to an UNASSIGNED IPR index. Real EV6 silicon IGNORES writes to unassigned IPRs: architecturally this is a no-op (per the AARM), with no fault. EmulatR instead raises kFaultUnimplemented and traps to the OPCDEC vector 0x8400 with excAddr=0x13655, which ABORTS sys__reset before sys__reset_init can run. FaultEventLog records this as FAULT[0] pc=0x13655 encoded=0x77e72d40 op=0x1d fault=3.

The fault is a deliberate SCAFFOLD, gated behind EMULATR_2D_NOOP in palBoxLib/grains/PalEntries.cpp. It was kept because aborting sys__reset lets the SRM reach >>> by SKIPPING the real-hardware init -- which is exactly the step that would otherwise build p_temp. Setting EMULATR_2D_NOOP=1 makes the write a faithful no-op and restores the real path. The downstream differs per platform: DS10 routes to a device poll at 0x13d38, ES40 to an MMIO DtbMiss at 0x1b7dd4, DS20 to the settling delay at 0x13e40 described later -- so keep the no-op DS20-scoped or fix those first.

 

sys__reset_init: building p_temp and the impure frame

With 0x2d no-op'd, sys__reset continues into sys__reset_init, which establishes the PAL temp region and links the impure / CNS save frame. From the DEC PAL source (ev6_vms_pc264_pal.mar, sys__reset :4315 -> sys__reset_init :4475 -> :4610):

GET_32CONS p_temp, PAL__TEMPS_BASE, r31 ; p_temp = PAL__TEMPS_BASE

addq p_temp, r1, p_temp ; + whami * PAL__TEMPS_SPECIFIC_SIZE (0 for primary)

GET_32CONS r2, PAL__IMPURE_BASE, r31 ; impure base

hw_stq/p r0, PT__WHAMI(p_temp) ; store whami @ +0x98

hw_stq/p r2, PT__IMPURE(p_temp) ; link impure base @ +0x88

EmulatR observes p_temp built at runtime by 0x138b8 LDAH r21,0 ; 0x138bc LDA r21,0x7000(r21), giving PAL__TEMPS_BASE = 0x7000 for DS20 ds20_v7_3. The PC264 def files list 0xF000 / 0x5000 -- the WRONG variant for DS20; trust the runtime 0x7000. It sits below palBase 0x8000 in free low DRAM (HWRPB at 0x2000, impure near 0x5000, PAL temps at 0x7000 -- distinct, all below the Tsunami MMIO gate 0x80000000000), so there is no image overlap. On the default (2D-faulting) path r21 instead stays the decompressor scratch 0xf01 (LDA R21,0xf01(R31) @0x600594), so PT__IMPURE(0xf01) reads garbage at the OS restart.

Breaking the wall: from RESET(0) to boot0 executing

Two fixes take DS20 from a dead RESET(0) at OS entry to boot0 actually executing. They are driven together by the wrapper tools/run_ds20_bplus.sh (exports EMULATR_2D_NOOP=1 + EMULATR_DELAYWARP=1 + the CSERVE mode, then execs run_ds20_showdev.sh).

1.FIX 1 -- EMULATR_2D_NOOP=1: sys__reset_init runs and builds p_temp=0x7000. CONFIRMED.

2.FIX 2 -- EMULATR_DELAYWARP=1 (a general SUBQ-countdown warp in PipelineDriver.h): collapses the settling delays at 0x13e40 / 0x13e80 / 0x13ec0 (~990M cyc) and reaches P00>>> at ~88 MHz effective. CONFIRMED.

With both applied, b dqa0 gives a valid boot block, reads 1226 blocks, and prints the full VMB banner (base=5bc000 image_bytes=99400, init HWRPB @ 0x2000, page table @ 0x3ff04000, "jumping to bootstrap code"). The halt PC advances from 0x20000000 (RESET) to 0x20000010 (boot0's first data access) -- boot0 is now EXECUTING. CAVEAT: do NOT run u srm in the LFU; update+exit triggers a ~407e9-cyc memory re-init spin, whereas a plain LFU exit re-inits in ~30e9 cyc.

 

boot0 disassembly and the mode gap

boot0 at VA 0x20000000 (PA 0x5bc000, leaf pfn 0x2de) is REAL VMB / APB code. Its first five instructions are position-independent setup that computes the HWRPB address and issues the first data load:

Address encoding instruction

Note

0x20000000 d3800000 bsr r28,0x20000004

PIC: r28 = own PC

0x20000004 201f0001 lda r0,1

0x20000008 203f001c lda r1,28

0x2000000c 48010720 sll r0,r1,r0

r0 = 1<<28 = 0x10000000

0x20000010 a4800050 ldq r4,0x50(r0)

LOAD VA 0x10000050 -- boot0's FIRST data access; the deterministic exit PC

The exit at 0x20000010 is boot0's first DATA reference. VA 0x10000000 IS mapped: l3[0] pte=0x100001101 leafPfn=0x1 leafPa=0x2000 -- the HWRPB, valid kernel R/W. So boot0 reads HWRPB+0x50, which is legitimate; the console's page table is COMPLETE and CORRECT. The cycle-ordered sequence is: seed intact -> ITBPROBE MISS then HIT va=0x20000000 pfn=0x2de (code fetch resolved) -> boot0 runs 4 instructions -> the ldq DTB-misses VA 0x10000000. The conclusion is decisive: this is NOT a missing map -- it is a MODE gap. A handoff that transfers the PC but NOT the OS execution mode / IPL / PS leaves boot0's data-miss to be serviced in an inconsistent context.

 

Why C++ replication (Option B) is a dead end

Option B (EMULATR_CSERVE_START_MODE=cpp / EMULATR_CSERVE_START_RESTART) has EmulatR's own C++ replicate exit_console: it reads the CNS via PT__IMPURE and installs PTBR = 0x1ff82 (the page table at PA 0x3ff04000) and VPTB = 0x200000000 (taken from hwrpb.vptb_va + 120, merged into VA_CTL / I_CTL), flushes ITB+DTB, and diverts to the halt PC. This got boot0 to FETCH (the JRN-VMB-001/002/003 wall broke), but live tracing then proved it cannot HOLD the machine in OS mode.

With EMULATR_PA_WATCH=0x7000, Option B seeds PT__VPTB(p_temp=0x7000) = 0x200000000, and ~480 cyc later a PA-WATCH STORE v=0x0 pc=0x1333c ra=0x62f6c ZEROES it. The guest DTBM_DOUBLE_3 VPTB self-test then reads 0 and crashes with halt code 0xA. The clobber is not a bug in the seed -- it is the guest firmware asserting itself: pc=0x1333c decodes exactly to ev6_vms_pc264_pal.mar:4162-4173 = sys__enter_console's "clear VPTB, switch VA_CTL to 48-bit 1-1 console mode." Its caller 0x62f6c is compiled SRM CONSOLE C code (LDQ r27,0x30(r2); BSR r26 -> 0x1ae328). In other words: after Option B diverts the PC to 0x20000000, control does NOT stay in OS boot0 -- it lands back in the SRM console, which runs enter_console and wipes PT__VPTB. This is hard proof that a C++ PC-divert plus PAL-temp seeding cannot hold the CPU in OS virtual mode. The mode is not a value you can set from outside; it is state the guest PAL owns.

 

The architectural model: CSERVE dispatch runs the guest PAL

The OS-boot handoff is NOT one intercept -- it is a SEQUENCE of CALL_PAL CSERVE functions the SRM console issues, each of which on real hardware runs a guest PAL handler. EmulatR's earlier mistake was intercepting CSERVE functions in C++ and either stubbing them or replicating their effects; that fights the PAL state machine and loses side effects. The correct, faithful model -- proven by AXPBox, which boots VMS -- is: route each CSERVE function to its guest PAL handler and let the real firmware execute. There is zero effect replication.

A note on references. AXPBox is a HANDOFF reference because it runs the real DEC PALcode. QEMU is NOT a handoff reference: it executes its own bespoke PALcode (it boots Linux with a different console/PAL), so it is useful only for EV6 instruction semantics, never for the console-to-OS handoff. EmulatR will NOT implement or imitate QEMU's PAL. SimH has no Alpha / EV6 target at all.

 

The guest CSERVE dispatcher and the AXPBox reference

The guest dispatcher is sys__cserve (ev6_vms_pc264_pal.mar:3852): it reads r16 (the function code) and branches to a per-function handler. Two handlers seen so far: cfw_start (:3956 = br sys__exit_console, the 0x42 START), and cfw_mp_work_request (:4017, saves r18 -> CNS__WORK_REQUEST, the 0x65 MP_WORK_REQUEST). CNS__WORK_REQUEST (checked at :886) is the console-to-CPU work mailbox; stubbing 0x65 means the item is never saved, so the coordination never completes and the console re-inits.

AXPBox (axpbox-1.1.2/src/AlphaCPU_vmspal.cpp, vmspal_call_cserve) is literally this: its FIRST line saves the CALL_PAL return PC into the PAL linkage register (p23 = state.pc), then a switch(r16) does set_pc(<guest PAL handler addr>) and lets the firmware execute the full faithful path (restore_state -> mode/vptb/IPL/TBIA -> hw_ret_stall(p23)). The routing invariant and Option A (mirror AXPBox)

Option A (EMULATR_CSERVE_START_MODE=guest, now the wrapper default) mirrors AXPBox exactly for the routed function. The invariant, to be applied for EACH CSERVE function routed to the guest PAL:

3.Set p23 (R23) = the CALL_PAL return PC = g.pc + 4. Set BOTH banks (intReg[23] and intShadow[7]) so the value survives the PAL-shadow swap around the divert. This is the PAL linkage register; the guest handler's terminating hw_ret_stall / hw_rei uses it. (Earlier Option A set excAddr / divertTarget but NOT p23, so exit_console's terminating hw_ret_stall(p23) landed on a stale R23 and reset.)

4.Divert the PC to the guest handler entry (PALmode, PC<0>=1). For START, the entry is the guest sys__exit_console, located by scanning the PAL image for the ITB_IA / DTB_IA signature pair (encodings 0x77FF0300 / 0x77FFA300, mask 0xFC00FF00) -- which is exactly cfw_start's br target.

5.Do NOT replicate the handler's effects in C++. The guest PAL sets mode / VPTB / IPL / the CNS frame / the work mailbox itself.

Result of applying this to START: the 0xA crash is gone, exit_console runs clean and returns to the console -- and the console then loops on CSERVE 0x65 MP_WORK_REQUEST, which EmulatR currently STUBS, so it re-inits. That is the point, not a regression: the next stubbed pure-PAL function becomes the next wall. The CLEANER GENERALIZATION is to scan for the sys__cserve ENTRY once and route ALL currently-stubbed CSERVE functions there with r16 intact -- the guest dispatcher then dispatches on r16 to the correct handler, so one divert covers every pure-PAL function uniformly. The console-I/O functions (PUTS / GETS / GET_ENV) legitimately need host interaction and MAY stay C++, but the pure-PAL coordination functions (START, MP_WORK_REQUEST, and the rest AXPBox set_pc's) MUST run the guest PAL.

 

The two homes of PT__VPTB

VPTB (the self-mapped page-table base) is stored in TWO places that must stay coherent: the PAL temp copy, and the impure frame at CNS__VPTB = impure_base + 0x268, where impure_base = mem[p_temp + 0x88] = mem[0x7088]. restore_state reads CNS__VPTB from the impure frame. The value 0x200000000 is NOT garbage -- it is the real VMS VPTB, sourced from hwrpb.vptb_va + 120. The Option B failure is the concrete lesson: when EmulatR seeds that derived VPTB into the PAL temp while the guest still owns the mode, the guest's own enter_console zeroes it. The faithful rule (P-1) is to let the guest's own restart machinery be the SOLE writer of the derived pal-temps, so the two homes are coherent by construction and the value's provenance is traceable to a single guest instruction.

 

The 0x13e40 settling delay (downstream of the 0x2d no-op)

No-op'ing 0x2d exposes a calibrated settling-delay loop at 0x13e40, a pure SUBQ countdown armed after programming Pchip1's DMA-window CSRs (WSBA0-3).

0x13e14-20 : HW_ST -> PA 0x803_8000_0000/40/80/c0 ; Pchip1 WSBA0-3 DMA windows

0x13e2c : LDAH R12,0xe5 ; R12 ~= 0xE4E1C0 (~15,000,000)

0x13e30 : LDA R12,-0x1e40(R12)

0x13e40 : SUBQ R12,#1,R12 ; pure countdown spin, no device read inside

0x13e44 : BEQ R12, exit

0x13e48 : BR -12 (back)

The older warps (EMULATR_IDLEWARP / UDELAYWARP / TICKWARP / RSCCWARP) target other loops (RSCC 0x7c304 etc.) and do NOT recognize 0x13e40, so 2D_NOOP alone stalls here (a further settle at 0xb740 follows). The fix (FIX 2, EMULATR_DELAYWARP=1) is a GENERAL SUBQ Rn-countdown-to-zero warp: recognize the SUBQ Rn / BEQ Rn / BR-back idiom, fast-forward Rn to 0, and advance the cycle counter by the skipped count. This covers 0x13e40, 0xb740, and siblings, and reproduces the delay's only architectural effect (elapsed time) without needing silicon's exact iteration count.

 

Platform lever: ISP vs silicon

The 0x2d fault and ISP mode are the same strategy -- skip the real-hardware init EmulatR does not yet model. In ISP (the default), EmulatR read-intercepts PA 0xBFFC -> 0xCAFEBEEF so the firmware's platform() returns ISP_MODEL and routes down the pre-silicon simulator paths that skip the unmodeled timing / probe / IDE steps. See Platform Execution Mode: ISP vs Silicon for the full lever, and WARP Variants and Cycle-Accounting for the delay-warp family.

 

Current status and next step

FIX 1 (2D no-op) and FIX 2 (delay warp) are CONFIRMED; the wall is broken and boot0 executes. Option B (C++ replicate) is a proven dead end (the seed is clobbered by console re-entry -- the mode gap). Option A (route START to the guest PAL, mirroring AXPBox's p23 save) is in flight and removes the 0xA crash. The well-scoped next step is to route CSERVE 0x65 (MP_WORK_REQUEST) to the guest PAL under the same invariant -- or, preferred, to locate the sys__cserve entry and route ALL currently-stubbed CSERVE functions there, so the guest dispatcher handles 0x65 and every future one. Then iterate b dqa0 and surface the next guest-PAL requirement. Diagnostics to remove once Option A lands: the CSERVE-DISASM dump, PTWALK BOOT0DATA/BOOT0VPTE, the CSERVE-START-BPLUS seeding, and the PA_WATCH default in the wrapper.
