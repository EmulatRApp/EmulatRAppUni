Per-CPU Halt Codes

When an Alpha processor stops and drops into console I/O mode, PALcode records WHY in the processor's per-CPU slot of the HWRPB. A developer reading an EmulatR trace or a console banner sees this value as the halt code. This page is the lookup table behind those numbers: the architected reason-for-halt set from the Alpha Architecture Reference Manual (AARM), the EV6 (21264) PALcode symbols EmulatR's PAL layer actually emits, and the companion halt-request field that system software sets to direct the console's next action. The authoritative references are the AARM (Table 26–4, per-CPU slot fields) and the apisrm EV6 PALcode sources under Processor Support/Palcode/.

 

Where the code lives

Each processor owns a per-CPU slot in the HWRPB. When a halt condition is encountered, PALcode captures the halting context and the reason into these slot fields (offsets relative to the slot base, AARM Table 26–4):

 

•+256 HALT ARGUMENT LIST – value of R25 at the halt.

•+264 HALT RETURN ADDRESS – value of R26 at the halt.

•+272 HALT PROCEDURE VALUE – value of R27 at the halt.

•+280 REASON FOR HALT – the code from the first table below. Set to 0 at console initialization.

 

The restart PC (HALT PC) and PS the console uses to resume live earlier in the slot; the boot handoff parks HALT PC at 0x20000000 (see Reset into Secondary Boot).

 

Architected reason-for-halt codes (AARM Table 26–4)

These are the values the architecture defines for the REASON FOR HALT quadword. Codes 0x8..0xFFF are reserved; values above that are implementation-specific (the EV6 realization is in the next table).

Meaning

0x0

Bootstrap / start / powerfail restart

Default. Set at console init and at every system bootstrap, processor start, or powerfail restart. Not an error.

0x1

Operator-requested crash

Console operator requested a system crash.

0x2

Kernel stack not valid

PALcode could not push state because the kernel stack was not valid (or misaligned) – a kernel-stack-not-valid halt.

0x3

Invalid SCBB

The System Control Block Base was invalid when PALcode tried to dispatch through the SCB.

0x4

0x5

The processor executed a CALL_PAL HALT instruction in kernel mode – the ordinary software-directed halt.

0x6

0x7

Reserved

EV6 (21264) PALcode realization

The apisrm EV6 PALcode (ev6_alpha_defs.mar, macro HALT_DEFS) names the architected codes as HALT__* symbols and adds implementation-specific ones for the D-cache tag-parity halt and the several console-entry dispatch reasons. These are the codes EmulatR's PAL layer works with; 0x8 and everything at 0x20 and above fall in the architected "implementation-specific" range.

Halt-request codes (the requested action)

Distinct from the reason-for-halt is the HALT REQUESTED field carried in the per-CPU slot STATE. System software (or firmware) writes it to tell the console what to do when the processor next halts; the console clears it after acting. The apisrm HWRPB definition (hwrpb_def.sdl, HALT_REQUEST$ prefix) enumerates:

0x0

0x1

HALT_REQUEST$SV_RST_TERM

Save state and restart / terminate.

0x2

HALT_REQUEST$COLD_BOOT

Perform a cold bootstrap.

0x3

HALT_REQUEST$WARM_BOOT

Perform a warm bootstrap.

0x4

Stay in console mode; do not restart.

0x5

HALT_REQUEST$POWER_OFF_SYSTEM

Power off the system.

0x6

HALT_REQUEST$RESERVED

Reserved.

0x7

HALT_REQUEST$MIGRATE

Migrate (transfer this CPU's role); used in the SMP / secondary path.

 

How EmulatR surfaces a halt

In V5 a halt condition is delivered as the kFaultHalt fault. The clearest path is the console-service HALT: CSERVE$HALT (function 0x40) in palBoxLib/grains/PalEntries.cpp mirrors the SRM cfw_halt – it corresponds to HALT__HW_HALT and returns kFaultHalt, and the run loop stops with StopReason::HaltedClean. The per-CPU slot's HALT PC parks at 0x20000000 for the OS boot handoff, so a stop at 0x20000000 in a trace is the transfer point, not a fault.
