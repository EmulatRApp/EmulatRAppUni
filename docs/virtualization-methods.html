Virtualization Methods

EmulatR can present the firmware with one of two execution-path identities. The choice is made by a single firmware routine -- the SRM console's platform() (apisrm pc264.c) -- which reads the 32-bit longword at physical address 0xBFFC and branches: the constant 0xCAFEBEEF selects ISP_MODEL (the pre-silicon simulator path), any other value selects REAL_HW (the faithful hardware path). EmulatR controls which branch the firmware takes through the EMULATR_PLATFORM environment variable; there is no second knob, because the firmware's own platform() is the single source of truth.

How the selection works

platform() reads *(int *)0xBFFC. EmulatR answers that read with a READ-INTERCEPT, never a deposit: 0xBFFC sits at firmware image offset 0x3FFC and is overwritten by the SRM self-decompressor during cold boot, so a one-time store would not survive to the moment platform() runs. The lever therefore lives in the load path (pipelineLib/MemDrainer.h): when the ISP method is active and the guest reads physical 0xBFFC, EmulatR substitutes 0xCAFEBEEF (sign-extended to match the firmware's constant). On the silicon method the read is not intercepted, so 0xBFFC returns its real memory contents and platform() resolves to REAL_HW.

 

ISP (virtual) path -- default

Active when EMULATR_PLATFORM is unset or set to any value other than the exact string "silicon" (the legacy alias "isp" also selects it). platform() returns ISP_MODEL, and the firmware takes its pre-silicon simulator branches -- skipping the real-hardware timing, probe, and IDE steps that EmulatR does not yet model. This is the path that reaches the SRM console prompt P00>>>. It is the out-of-box behavior and the path used for all current console-and-boot work.

 

Silicon path -- hardware initialization

Active when EMULATR_PLATFORM is set to exactly "silicon".

 

EMULATR_PLATFORM=silicon

platform() returns REAL_HW, and the firmware runs the faithful hardware-initialization sequence (the same code path real Alpha silicon would execute).

 

This exercises the real timing/probe/device-init steps, so it takes substantially longer to initialize. IMPORTANT: REAL_HW is currently largely unmodeled in EmulatR, so this path may not reach P00>>> -- it can grind in the hardware-probe steps and run until the cycle limit (MaxCyclesExceeded).

 

Stop a run cleanly by creating the file EMULATR_STOP in the run directory (this flushes flash NVRAM on exit).

 

The value of running it today is comparative:

 

it shows whether the firmware's deterministic init sequence (for example, the order of IIC bus init versus HWRPB construction, and the resulting system-type badge) behaves differently from the ISP path.

 

Invocation examples

From the build/run directory (out/build/release). Console is on TCP 10023.

 

# ISP (virtual) path -- default; reaches the SRM prompt

./run_fw.sh ds20 cold

 

# Silicon path -- full hardware init (slow; may not reach the prompt)

export EMULATR_PLATFORM=silicon

export EMULATR_FLASH_ROM=ds20_flash.rom; rm -f ds20_flash.rom # factory-fresh cold

./run_fw.sh ds20 cold 2>&1 | tee fw_ds20_silicon.out

touch EMULATR_STOP # stop a long silicon run cleanly

 

Notes

The EMULATR_PLATFORM lever (2026-06-19) supersedes the temporary EMULATR_CPU1_ALIVE flag. Do not add a second host-side sim/silicon flag -- the firmware's platform() is the single source of truth, and EmulatR's only role is to answer the 0xBFFC read consistently with the chosen method. Selection is evaluated once per run (a function-local static), so changing EMULATR_PLATFORM requires a fresh run.
