HWRPB Key/Value Offset Map

This page documents the kKeyValue offset map for the HWRPB (Hardware Restart Parameter Block) and its chained structures, as encoded in deviceLib/Hwrpb.h. It is a navigation aid; the authoritative layout is the AARM Section III "Common Architecture, Console Interface" (Table 26-1 header, Table 26-4 per-CPU slot), cross-referenced against the read-only apisrm/srmapi SSOT and the live DS20 SRM dump. EmulatR is the only tree edited; apisrm/srmapi is never modified.

The kKeyValue pattern

Each HWRPB field has a convenience constexpr "key = value" constant (value is the field's byte offset from its region base), in the same spirit as kAlphaPageSize. A field can then be reached two equivalent ways: by typed struct member, or by offset key over a raw byte window through a View union. The two paths are pinned together by static_asserts so they can never silently drift.

 

// offset keys (constexpr uint64_t, like kAlphaPageSize = 8192)

constexpr uint64_t kSlotStateFlags = 0x080;

constexpr uint64_t kSlotCycleCounterFreq = 0x270;

constexpr uint64_t kSlotSize = 0x280;

 

// View union: overlay a raw byte window with the typed struct

union PerCpuSlotView { uint8_t raw[kSlotSize]; PerCpuSlot fields; };

 

// typed-member path and offset-key path are equivalent:

uint64_t a = view.fields.state.raw;

uint64_t b = peek<uint64_t>(view.raw, kSlotStateFlags); // a == b

poke<uint64_t>(hdrBase, kHwrpbSystemVariation, 0x1805); // DS20 SYSVAR

 

peek/poke are memcpy-based, so they are alignment- and strict-aliasing-safe wherever the base points in guest memory. Host (x86_64) and guest (Alpha) are both little-endian and the structs are #pragma pack(1), so the overlay is byte-faithful.

Per-CPU slot offset keys (AARM Table 26-4)

The slot stride is 0x280 (640 bytes): the AARM fields end at Cycle Counter Frequency (+624, last byte +631), padded to an octaword. This matches the live DS20 SRM. The five fields at +592..+624 were previously hidden in an opaque filler, and an in-slot DSRDB had inflated the slot to 0x400 (corrected 2026-06-29).

Note (PALCODE REVISION): the AARM defines +168 as one bit-packed quadword (bits 63:48 max processors sharing this PALcode, 47:32 compatibility, 23:16 variation, 15:8 major, 7:0 minor). EmulatR keeps a pal_rev/pal_var u32 split at 0x0A8/0x0AC: the offset is correct, but the high 32 bits (max-procs + compat) are not separately modeled. Widen when the PAL-rev publishing path is reworked.

 

Note (REASON FOR HALT): the AARM halt codes (0 boot, 1 operator crash, 2 kstack-not-valid, 3 invalid SCBB, 4 invalid PTBR, 5 CALL_PAL HALT in kernel, 6 double-error, 7 machine-check in PALcode) do not match EmulatR's HaltCode enum numbering. Reconcile before relying on the halt reason cross-process.

 

DSRDB section offset keys

The DSRDB (Dynamic System Recognition Data Block) is a separate top-level HWRPB section reached via kHwrpbDsrdbOffset (+312), found live on DS20 at PA 0x2ac0. It is NOT part of the per-CPU slot (it was incorrectly embedded there before 2026-06-29). Validate this layout field-by-field against the live 0x2ac0 dump before relying on it.

Correctness: keys pinned to struct offsets

A block of static_asserts at the end of Hwrpb.h ties each key to the matching offsetof() in its struct, so the typed-member path and the offset-key path can never silently diverge as the layout evolves:

 

static_assert(kSlotCycleCounterFreq == offsetof(PerCpuSlot, cycle_count_freq), "key/cycle_count_freq");

static_assert(kHwrpbSystemVariation == offsetof(HwrpbHeader, system_variation), "key/sysvar");

 

Verified with g++ -std=c++17: the header compiles clean and every static_assert passes (PerCpuSlot = 0x280, HwrpbHeader = 320, Dsrdb = 0x100, cycle_count_freq at 0x270).
